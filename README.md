# My Finances

Next.js App Router application with PostgreSQL, Prisma 7, and Better Auth email/password authentication.

## Local setup

1. Install dependencies with `npm install`.
2. Copy `.env.example` to `.env` and set `DATABASE_URL` to your PostgreSQL database.
3. Set `BETTER_AUTH_URL=http://localhost:3000` and generate a secret:
   `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`
   Store the result in `BETTER_AUTH_SECRET`.
4. Apply migrations with `npm run db:deploy`.
5. Run `npm run dev` and open http://localhost:3000/register.

Prisma Client is generated during installation. Run `npm run db:generate` after schema changes, `npm run db:migrate -- --name your_change` to create a migration, or `npm run db:studio` to inspect local users.

## Authentication

All five models use a string `id` generated by Prisma's `cuid()` default and a separate, unique `number` generated by PostgreSQL. Better Auth delegates ID generation to Prisma with `advanced.database.generateId: false`. Relations and authorization continue to use string IDs; `number` is a display/reference number, unique within its table, not across models. Sequence numbers may have gaps.

The `number` field is registered as server-owned additional data for users, sessions, accounts, and verifications; client-side user/session types infer it from the auth configuration. The application session helper also includes `user.number`. Rate-limit numbers stay internal and are accessible through Prisma. Do not accept `id` or `number` from registration forms or manually calculate sequence values.

User verification is stored exclusively in `User.emailVerifiedAt`: `null` means unverified, a timestamp means verified. The local Better Auth plugin converts the library's internal boolean to/from this column. Application code receives `user.emailVerifiedAt` through `getSession()` and `requireSession()`; Better Auth's own HTTP/client responses retain its boolean contract. Maintain the Prisma schema directly: Better Auth schema generation would infer a boolean column from its internal contract.

- `/register`: name, email, password, and password confirmation; registration signs the user in.
- `/login`: email/password login.
- `/`: protected account page with logout. Signed-in users are redirected away from authentication pages.
- `/api/auth/[...all]`: Better Auth handlers with origin checks and database-backed rate limits.
- Users have unique email addresses. Better Auth stores salted scrypt password hashes in the related `Account.password` field for the credential provider, never plaintext passwords on `User`.
- Passwords have no length or complexity rules; a non-empty password is required. Sessions expire after seven days and are revoked on logout.
- Call `requireSession()` in each protected server page/action; check sessions and resource ownership in future API endpoints too. Do not rely on the UI for authorization.

OAuth is a protocol for delegated authorization. This implementation uses Better Auth's password authentication; Google/GitHub OAuth providers are not configured. Email verification and password recovery require an email provider and are not enabled.

## Partners

`/partners` lists the signed-in user's partners and provides creation, editing, and deletion for name, type, email, notes, and contact link. String IDs and reference numbers are generated automatically. Every read and mutation is scoped to the authenticated owner's string ID on the server; submitted owner IDs or numbers are not accepted. Optional empty fields are stored as `null`. Contact links accept HTTP/HTTPS URLs.

Deletion requires confirmation in the UI and also removes an existing `PartnerUserLink` through the schema's cascade. Creating or managing user-link invitations is not part of the partner form. The existing `add_partner_structure` migration and generated Prisma models are used.

## Deployment and validation

Set the three environment variables for the deployment, use an HTTPS `BETTER_AUTH_URL`, run `npm run db:deploy`, then `npm run build` and `npm start`. Keep the secret stable across instances. Better Auth uses secure cookies in production. Configure your trusted reverse proxy to overwrite client IP headers so rate limits cannot be bypassed by spoofing headers.

Do not run tests, lint checks, or builds after changes unless explicitly requested.
With the app running, `npm run test:auth` tests registration, password hashing, duplicate/invalid credentials, session protection, origin rejection, rate limiting, and logout against the configured database; it removes its own test user afterward. Run only against a development/test database.

Integration follows the [Better Auth Prisma adapter](https://better-auth.com/docs/adapters/prisma) and [Next.js integration](https://better-auth.com/docs/integrations/next) documentation.
